# BCM4752 post-ESW hand-off to GLME — exact vendor sequence and current hardware state

Target: SM-J700M `j7elte`, kernel `3.10.108 #33` (stock-parity GPS driver),
BCM4752 HW `0x30020005`, `/dev/ttySAC0` 921600 8N1. Tools:
`code/userspace/gps/src/gpsesw.c`, stock `/tmp/stock_gpsd` (the image's
`/system/bin/gpsd`), and the existing chroot rig (`docs/reports/gps-chroot.md`).

**Verdict in one paragraph.** The host-side hand-off the vendor daemon performs
after the RAM patch was recovered **exactly**, without guessing, by running the
stock daemon in the chroot against a PTY with a small BCM4752 BRI emulator on
the other end: after the last `2f 15` CRC acknowledgement of the **third** block
it sends `fe 00 fd 00 00 55 aa 00 ff fc` immediately, with **bank 1 still
selected**, and no readbacks of any kind. The stock daemon also **never sends
the synthetic `0x7fd2` record** on `4752_B2`; our uploader did, and that record
overlaps block 0. The corrected sequence is implemented as `gpsesw --golden`
and was replayed end-to-end (including banner detection) against the emulator.
It has **not yet produced a banner on real silicon**: the chip was left mute for
BRI by an earlier switch and power gating does not reset it. The hardware test
needs a cold boot; the command and the expected capture are in §8.

Evidence tags: **[OBS]** = observed on the wire by the stock daemon (PTY
emulator) or on hardware; **[HW]** = observed on this phone's chip;
**[INFERENCE]** = reading, not confirmed.

---

## 1. New ground truth: stock daemon on a PTY

The chroot setup of `docs/reports/gps-chroot.md` was reused, with one change:
`gps.xml` `PortName` was pointed at a PTY (`/dev/pts/N`, exported into the
chroot with `mount --bind /dev/pts`) and `GpioNStdbyPath` at a scratch file, so
the real chip was not touched. The emulator on the master side:

* answers the 16×`0x80` burst + sync frame with the same sync frame,
* answers `ff 00 fd 00 00 fc` with `fe 00 fd 00 00 05 00 02 30 fc`,
* answers item reads with the requested item and a value (0x94 = selected bank,
  0x95 = 0, 0x1b = 7),
* tracks `fe 00 fd 61 16 <bank>` writes silently,
* acknowledges every `21 18 <addr> <len>` with the **real hardware values**
  captured earlier (`docs/reports/gps-esw-upload.md` §2),
* logs every host frame, and answers the `0x55aa` switch with the published
  banner `e0 … e0 01`.

Scripts live at `/data/opt/stock/tmp/{gpsemu.py,run_pty.sh}` on the device
(generated by this slice; not part of the repo). Raw capture of the decisive run
is `/tmp/stock-capture.log` on the device.

There is **no** frame between the last `2f 15` reply and the `0x55aa` switch,
and **no** `0x7fd2` block (the CRC request list is exactly four entries:
`7000`, `7fec`, `8000`, `9000`). Bank state at the switch is **1**.

### 1.2 The payload bytes are identical to our extracted blocks **[OBS]**

The emulator's captured data frames were reassembled and compared with
`/tmp/gps_esw/b2-4752_B2-{0,1,2}.bin`: all three match byte-for-byte
(SHA-256 prefixes `79f09f9d7ee3bff5`, `a63be51b45b90365`, `fdb57d8df7f2da56`).
The stock daemon sends the same patch, in the same 1020-byte chunks with the
same odd-tail frame. The block-2 tail frame is `fe01…9a75` + the last four
bytes, exactly as our encoder emits it.

### 1.3 The vendor validates the 2f15 value (and retries on mismatch)

The emulator run exposed this by accident. Replying `fe00fd2f1500000000fc`
(zeros) to every CRC request made the stock loader **retransmit the whole
block five times** and then restart the init; replying with the values this
phone's chip actually returns made it proceed on the first try. The
disassembly agrees: at `0x2a779c` the CRC-received handler compares the stored
reply (`[obj+0x13c]`) with the loader's own value (`0x2a8e88`), and
`0x2a77ec` treats a mismatch as failure (`cmp r5,#0; beq error`). So the
capture in §1.1 is the normal, CRC-validated path, not an error path, and it
also explains why the values we feed the emulator must be the real ones.

### 1.4 Why this is not an emulator artefact

The same conclusion is visible in the disassembly, independent of the PTY run
(`/tmp/stock_gpsd`, Thumb-2, file offset == vaddr):

* `0x2a7690` is the patch-loader packet state machine. On the packet that
  carries a `2f 15` acknowledgement it advances the block (`0x2a9270`); if that
  returns 0 (no next block) it calls `0x2a618c` and returns (`0x2a785c`,
  `0x2a7860`).
* `0x2a618c` is `Bri_GetOutOfLegacy()`: it builds exactly one 10-byte frame
  from the table entry at base `0x398754 + 0x3d8` and sends it via `0x2a5cd0`.
  The bytes at `0x398b2c` are `fe 00 fd 00 00 55 aa 00 ff fc`.
* The bank-switch builder `0x2a5ce4` writes `fe 00 fd 61 16 <bank> 00 00 00 00 fc`
  and then reads item `0x94`; the loader calls it when the bank byte of the
  next record differs from the current bank (blocks 0/1 bank 0, block 2 bank 1).
* The record lookup (`0x2da0fc`) does have a synthetic index 3
  (`0x7fd2`, 4 zero bytes, `0x2da196`), but the per-revision send loop stops at
  index 2 for `4752_B2` — confirmed by the absence of a fifth CRC request in
  the capture and by the stop predicate `0x2a8cc4` comparing the index with the
  loader's limit field.

## 2. What was wrong with the previous attempts

`docs/reports/gps-esw-upload.md` §5 listed three failed variants. Two details
now stand out, one proven and one inferred:

1. **The `0x7fd2` record was sent. [OBS]** Block 0 covers
   `0x7000…0x7fdb`; the synthetic record writes four zero bytes at
   `0x7fd2…0x7fd5`, i.e. **inside the block-0 image already in the chip**.
   Block 0 contains `01 00 00 00 75 fe 01 02` at `0x7fd2`; zeroing the first
   four bytes of that structure is a plausible patch destroyer **[INFERENCE]**.
   The vendor daemon never sends this record for `4752_B2`.
2. **The switch was sent after four readbacks with bank 0 selected. [OBS]**
   The old path ends block 2 (bank 1), switches back to bank 0, loads `0x7fd2`,
   then reads `0x94`, `0x95`, register 0 and item `0x1b` before the switch.
   The vendor sends the switch with bank 1 still mapped and **no** readbacks.

Both are encoded as separate variants, so a cold-boot test can isolate them.

## 3. Hardware result of the corrected hand-off

On 2026-11-19 00:24 the corrected post-patch sequence (blocks 0–2 only,
immediate switch, bank 1, no readbacks) was run on the chip with the normal
prologue (`-H 1`, the predecessor of `--golden`). All four acknowledgements were
the known hardware values:

```
00:24:33.904 gpsesw: CRC ACK 2f15 value=0xf107730c     ; 0x7000/4060
00:24:34.225 gpsesw: CRC ACK 2f15 value=0xec000075     ; 0x7fec/4
00:24:35.257 gpsesw: CRC ACK 2f15 value=0x8109aed2     ; 0x8000/4096
00:24:35.637 gpsesw: CRC ACK 2f15 value=0x0b05ed95     ; 0x9000/2681
00:24:35.638 gpsesw: all blocks sent (handoff variant 1); post-patch state
00:24:35.638 gpsesw: GLME switch
        (        glme-rx: no bytes in 3000 ms)
        (        tail: no bytes in 100 ms)
```

Raw switch frame (from the same log):

```
        tx (10): fe 00 fd 00 00 55 aa 00 ff fc
```

So: **no banner**, no bytes at all in 3 s. This was the first attempt with the
corrected post-patch order, but it still used the old prologue (16×`0x80`, then
the `0x001b`/`0x401a` exchanges), not the vendor's sync-frame prologue.

Caveat on how strong this negative is: a query-only run immediately before it
succeeded and read item `0x98` = 1 (no patch marker), but the chip had **not
been cold-booted** since the earlier four-block attempts, and power gating is
known not to reset it. Its RAM may therefore still have held the image
corrupted at `0x7fd2` by the old sequence, and a re-upload is not proven to
replace it. The cold-boot run in §8 is the decisive test; this hardware result
only rules out the combination on a chip that had been power-cycled, not on
virgin silicon.

### 3.1 Chip state afterwards — mute for BRI

A query-only run right after the switch:

```
00:24:58.046 gpsesw: prologue: 3 of 5 exchanges answered   ; 0x95 silent
00:25:00.453 gpsesw: item 0x94 = 0x00000001
00:25:01.657 gpsesw: item 0x98 = 0x00000001
```

A second query-only run after **20 s of `GPS_PWR_EN` low**:

```
00:27:22.208 gpsesw: prologue: 4 of 5 exchanges answered
00:27:22.509 gpsesw: item 0x94 = 0x00000001
00:27:25.521 gpsesw: item 0x98 = 0x00000003               ; ESW still resident
```

So a 20 s power cycle restored partial BRI but **did not reset the chip**:
the patch is still resident (`0x98 = 3`) and `0x95` does not answer.

Finally, the vendor prologue was tried on that half-mute chip (first without a
power cycle, then after another 20 s low):

```
        tx (10): fe 00 fd 21 00 01 33 0e 10 fc
        (        rx: no bytes in 300 ms)
        tx (6): ff 00 fd 00 00 fc
        (        rx: no bytes in 300 ms)
        tx (6): ff 00 fd 1f 95 fc
        (        rx: no bytes in 300 ms)
00:29:00.020 gpsesw: prologue: 0 of 3 exchanges answered
```

This is inconclusive about the sync frame itself (the chip was already mute
before it), but it shows the chip does not recover by itself.

## 5. `gpsesw --golden`

`code/userspace/gps/src/gpsesw.c` now implements the recovered sequence as one
deterministic flag:

* loads only blocks 0, 1, 2 (the `0x7fd2` record is not loaded or sent) —
  `nblocks = 3` before the load loop, so a missing `b2-…-3.bin` is irrelevant;
* sends no post-patch readbacks;
* leaves the last `61 16 01` (bank 1) in effect;
* sends `fe00fd000055aa00fffc` immediately after the last `2f15` reply;
* listens for 3 s (unless `-L` is given) and scans the received bytes for a
  GLME frame delimited by `e0 00 … e0 01`;
* prints `GLME banner received: hand-off works` and exits 0 on success, or
  `no GLME banner in N ms: chip is mute for BRI; a cold boot (device reboot) is
  required before another BRI/ESW attempt` and exits 7 on silence.

Default behaviour with no `--golden` is unchanged (`-H 0`). Related flags:
`-H 1..6` (individual post-patch variants, see table) and `-B 1` (vendor
prologue: 16×`0x80` immediately followed by the sync frame
`fe00fd210001330e10fc`, then register-0 and item-`0x95` reads).

Validation: both `--golden` and `--golden -B 1` were run against the PTY
emulator with `-d /dev/pts/N -n`. In each case the emulator saw exactly bank 0
→ blocks 0/1 → `2f15` → bank 1 → block 2 → `2f15` ×2 → `55aa`, with no
`0x7fd2` frame; the `-B 1` run also saw the sync frame echoed before anything
else (`prologue: 3 of 3 exchanges answered`). Both reported `GLME banner
received: hand-off works` and exited 0. This checks the tool side end-to-end
without the chip.

## 6. Banner

The banner is not a BRI frame. It is `e0 00 <payload> e0 01`; the published
capture is:

```
e0 00 00 00 07 10 02 01 7e 06 30 02 00 05 50 e0 01
```

`30 02 00 05` inside it is the little-endian ASIC id `0x30020005`, i.e. this is
a GLME version/status frame identical in shape to the public-spec capture.
What the chip emits **next** is not yet observed on this phone: the public
capture shows GLME configuration traffic follows, but the chip never left BRI
here, so there is nothing to decode. `gpsesw` prints every byte of the 3 s
window after the switch (`glme-rx`), so the first successful run will record the
banner and the following frames verbatim.

## 7. Recovery rules (important)

* **Power gating is not a reset.** 20 s of `GPS_PWR_EN` low left the patch
  resident (`0x98 = 3`) and BRI half-mute. Do not burn experiments assuming a
  clean chip.
* **A cold boot (device reboot) is the only known recovery** to a clean BRI
  state. One candidate per boot.
* Do **not** disable the candidate GPS rails (`ldo38`, `ldo39`) to force a
  reset: they are always-on with no listed consumer and an unknown fan-out;
  cutting them can brown out unrelated IP (decision recorded with the main
  coordinator).
* If a run ends with `no GLME banner … cold boot required`, stop; do not send
  more BRI frames or another switch.

## 8. Cold-start test plan

After a reboot, with the chip at BRI and nothing else holding `/dev/ttySAC0`:

```
# one candidate per cold boot
flock /tmp/gpsdev.lock /usr/local/bin/rootshell \
  /data/opt/stock/tmp/gpsesw-new -D /data/opt/stock/tmp/gps_esw \
  --golden > /tmp/golden.log 2>&1
echo $?          # 0 = banner, 7 = mute (needs reboot), 4 = prologue failed
```

Expected transcript on success:

| step | host frame | expected reply |
|---|---|---|
| prologue | 16×`80`, `fe00fd001b07000000fc`, … | ≥3 of 5 answered |
| bank 0 | `fe00fd611600000000fc`, `ff00fd1f94fc` | `fe00fd1f9400000000fc` |
| block 0 | 4 data frames + `fe00fd21180070dc0ffc` | `fe00fd2f150c7307f1fc` |
| block 1 | 1 data frame + `fe00fd2118ec7f0400fc` | `fe00fd2f15750000ecfc` |
| bank 1 | `fe00fd611601000000fc`, `ff00fd1f94fc` | `fe00fd1f9401000000fc` |
| block 2 | 6 data frames + tails, `fe00fd211800800010fc`, `fe00fd211800900a79fc` | `fe00fd2f15d2ae0981fc`, `fe00fd2f1595ed050bfc` |
| switch | `fe00fd000055aa00fffc` | `e0000000071002017e063002000550e001` then GLME frames |

**Order to try.** The full vendor parity command (`--golden -B 1`) is the
better first shot after a cold boot, because it also removes the one remaining
non-stock prologue element: the `0x001b <- 07` write that the old prologue
sends. The stock daemon never writes item `0x001b`, and that write is a
plausible reason for a loaded patch not to start. It also sends the sync frame
that stock and the public capture both use. Only if that fails on a clean chip
should the proven-prologue variant be tried:

```
# first, full vendor parity (sync-frame prologue + golden hand-off)
flock /tmp/gpsdev.lock /usr/local/bin/rootshell \
  /data/opt/stock/tmp/gpsesw-new -D /data/opt/stock/tmp/gps_esw \
  --golden -B 1 > /tmp/golden-b1.log 2>&1

# second (new boot), only if the first failed:
flock /tmp/gpsdev.lock /usr/local/bin/rootshell \
  /data/opt/stock/tmp/gpsesw-new -D /data/opt/stock/tmp/gps_esw \
  --golden > /tmp/golden.log 2>&1
```

The `-B 1` run must first echo the sync frame (`fe00fd210001330e10fc`); if the
sync does not echo but register 0 and item `0x95` do, the run continues (2 of 3
accepted). If it fails at the prologue itself, the sync frame is not usable on
this boot and the chip likely needs another cold boot before the fallback.
One candidate per boot: a failed hand-off leaves the chip mute.

On success, the remaining work is the GLME layer (configuration/measurement
frames after the banner); the BRI/ESW side is then complete and `--glme` in
`j7elte-gpsd` can be wired to the same golden sequence.
