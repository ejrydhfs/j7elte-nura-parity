# Bluetooth parity — Broadcom BCM43438 / Samsung `bcm43xx` (j7elte)

Scope: ROM `SM-J700M J700MUBU2BRC2` (kernel 3.10.61-13213628) vs Nura kernel tree
`android_kernel_samsung_universal7580-2a746c1…` (3.10.108). Driver code and config are
compared statically; the three j7elte device trees are additionally compiled
(`cpp` + `dtc`) and compared node-for-node against the three ROM DTBs. No kernel code
was cross-compiled and no runtime test was performed.

**Verdict: GAP-PATCHED.** The driver source itself is at parity. Two items failed on the
baseline and both now have apply-checked fixes:

* P2 — the `bluetooth` node's `bt_en` pinctrl group targets the wrong pin (gpa1-6
  instead of gpc4-2) on every j7elte board revision. Fixed for **all three ROM
  revisions** (rev00/rev04/rev06) by
  `parity/patches/bluetooth/0001-j7elte-bt-pinctrl.patch`: a ROM-identical `bt-en`
  group (`gpc4-2`, function=1, pud=0, con-pdn=3, pud-pdn=0) is added to each
  per-revision gpio dtsi (`exynos7580-j7elte_gpio_{00,04,06}.dtsi`, inside
  `&pinctrl_7` = `pinctrl@138D0000`, the gpc4 bank, exactly where the ROM puts it)
  and each `bluetooth` node is pointed at it. With the patch applied, all
  BT-relevant DT nodes are value-identical to the corresponding ROM DTB for
  rev00, rev04 and rev06 (see P2).
* P3 — the config had no HCI transport (`CONFIG_BT_HCIUART`/`H4`), which BlueZ needs on
  Linux. The ROM did not need it because Android's `libbt-vendor.so` implements the UART
  HCI transport and patch-RAM download entirely in userspace; BlueZ cannot. Fixed:
  `CONFIG_BT_HCIUART=y` + `CONFIG_BT_HCIUART_H4=y` are already applied in the pmaports
  working tree by the parent
  (`parity/pmaports/device/archived/linux-samsung-j7elte/config-samsung-j7elte.aarch64:918-919`)
  and are captured as `parity/patches/bluetooth/0002-j7elte-bt-hci-config.patch` against
  the pmaports baseline.

| Item | Result |
|---|---|
| P1 symbol coverage | **PASS** — 328/328 ROM BT symbols accounted for (326 exact source matches, 2 macro-generated module init/exit aliases) = 99.4 % raw / 100 % explained |
| P2 device tree | **FAIL on baseline → GAP-PATCHED (0001)** — `bluetooth` node, gpios, UART pinctrl and `bt_dummy` match on baseline; `bt_en` group is `gpa1-6` (Nura) vs `gpc4-2` (ROM) on all three revisions. With `0001` applied, every BT-relevant node is value-identical to the ROM DTB for rev00/rev04/rev06 |
| P3 config | **FAIL on baseline → GAP-PATCHED (0002)** — driver builds (`CONFIG_BT=y`), but `CONFIG_BT_HCIUART`/`CONFIG_BT_HCIUART_H4` were unset; the parent has applied them in the pmaports working tree (see P3) |
| P4 firmware | **PASS (artifact + mapping)** — the ROM blob is extracted and hashed; consumer is userspace, mapping in `parity/firmware/files-bt.list`; blob packaging is handled by the parent's `firmware-samsung-j7elte` pmaports package, userspace attach step still required (G1/R1) |

### The one delta — `bt_en` pinctrl group

The ROM's `bt-en` group is a child of `pinctrl@138D0000` (the gpc4 bank) and configures
**gpc4-2** (`000_800.dts:2264-2272`):

```
bt-en {
        samsung,pins = "gpc4-2";
        samsung,pin-function = <1>;
        samsung,pin-pud = <0>;
        samsung,pin-con-pdn = <3>;
        samsung,pin-pud-pdn = <0>;
};
```

Nura's `bt_en: bt-en` group is a child of `pinctrl@139B0000` (gpa bank) and configures
**gpa1-6** (`exynos7580-pinctrl.dtsi:62-68`, inside the node that starts at `:16`):

```
bt_en: bt-en {
        samsung,pins ="gpa1-6";
        ... same function/pull/pdn values ...
};
```

`bt_btwake` (gpa2-2, func 1, pud 0) and `bt_hostwake` (gpa2-6, func 0, pud 0) are equal
(`exynos7580-pinctrl.dtsi:84-94` vs ROM `:154-168`). The `bt_en` group is shared with
every board that uses `&bt_en`; only a3xelte has BT_EN on gpa1-6, while j7elte (and the
other gpc4-2 boards) do not. j7elte marks gpa1-6 as `NC`
(`exynos7580-j7elte_gpio_00.dtsi:38`), so the stray mux is harmless in itself, and
`gpio_direction_output()` still muxes gpc4-2 as an output through
`drivers/pinctrl/pinctrl-samsung.c:920-934`. The real loss is the deep-sleep config
(`pin-con-pdn = 3`, i.e. BT_EN driven low in suspend) that the ROM applies to gpc4-2.

Fix (apply-checked; DT ownership `arch/arm64/boot/dts/exynos7580-j7elte*.dts*`):
`parity/patches/bluetooth/0001-j7elte-bt-pinctrl.patch` adds a ROM-identical `bt-en`
group for gpc4-2 to **each** per-revision gpio dtsi — inside `&pinctrl_7`
(`pinctrl@138D0000`, the gpc4 bank controller, exactly where the ROM places the group) —
and points each `bluetooth` node at it. The compiled node name is `bt-en`, matching the
ROM node name exactly; the label `bt_en_j7` only distinguishes it from the shared
`bt_en` group and is stripped by `dtc`:

```diff
--- a/arch/arm64/boot/dts/exynos7580-j7elte_gpio_00.dtsi   (identical change in _gpio_04.dtsi / _gpio_06.dtsi)
+++ b/arch/arm64/boot/dts/exynos7580-j7elte_gpio_00.dtsi
@@ -392,6 +392,14 @@
 	pinctrl-0= <&sleep7>;
 
+	bt_en_j7: bt-en {
+		samsung,pins = "gpc4-2";
+		samsung,pin-function = <1>;
+		samsung,pin-pud = <0>;
+		samsung,pin-con-pdn = <3>;
+		samsung,pin-pud-pdn = <0>;
+	};
+
 	sleep7: sleep-state {
--- a/arch/arm64/boot/dts/exynos7580-j7elte_rev00.dts   (identical change in _rev04.dts / _rev06.dts)
+++ b/arch/arm64/boot/dts/exynos7580-j7elte_rev00.dts
@@ -1226,7 +1226,7 @@
-		pinctrl-0=<&bt_hostwake &bt_btwake &bt_en>;
+		pinctrl-0=<&bt_hostwake &bt_btwake &bt_en_j7>;
```

The patch touches exactly six files (`git diff` over
`arch/arm64/boot/dts/exynos7580-j7elte*.dts*`): `exynos7580-j7elte_gpio_{00,04,06}.dtsi`
(one per revision — each gpio dtsi is included by exactly one rev DTS) and
`exynos7580-j7elte_rev{00,04,06}.dts`. It does not edit the shared `bt_en` group
(`exynos7580-pinctrl.dtsi:62-68`), which a3xelte needs for its real gpa1-6 BT_EN, and it
leaves `pinctrl-names = "sleep"` / `sleep7` (incl. `PIN_SLP(gpc4-2, PREV, NONE)`) alone.

Verification: `git -C <kernel-tree> apply --check` **and** `git apply --check --cached`
against the clean baseline → `APPLY_OK` (`parity/verify.sh` → `OK`); the kernel tree was
restored to the baseline afterwards (working tree clean).

## P4 — firmware

### ROM: userspace-loaded, not kernel

* ROM firmware file: `/vendor/firmware/bcm43438A1_V0051.0230.hcd`, 35 307 bytes
  (`debugfs -R "ls -l /vendor/firmware" system.raw`). It is the only `.hcd` there.
* Extracted to `parity/firmware/bcm43438A1_V0051.0230.hcd`;
  sha512 `5d563e9d6cc34efc4ae82e6b46b016daca04530243f3351373b528f82865eb95973154665e63f9694785be7bb40465b6577d5a4d021f854caba63941c8440365`
  (now also recorded in `parity/firmware/MANIFEST.sha512`). Header commands are
  `0xfc4c` (`Write_RAM`) and the embedded string is
  `%BCM43438A1 37.4MHz J7-LTE BT4.0-0051`, confirming chip/board identity.
* No kernel consumer exists in either kernel:
  `grep request_firmware drivers/bluetooth/bcm43xx.c` → none; the 3.10 tree has no
  `btbcm.c`/`hci_bcm.c`; the ROM image contains no `BCM43438`/`brcm/`/`.hcd` strings and
  no `btbcm_*` symbols.
* The ROM consumer is `/lib/libbt-vendor.so` (dumped from `system.raw`). Its strings:
  `/vendor/firmware/`, `.hcd`, `module conf file not found; use default file extension .hcd`,
  the supported-chip table `BCM43241`, `BCM43341`, `BCM43438A1`, `BCM4345C0`, the board
  suffixes `_semco_b1.hcd`, `_murata_b1.hcd`, `_semco.hcd`, `_murata.hcd`, `_wisol.hcd`,
  and `/dev/ttySAC3`. This matches `BT_UPORT 3` / `ttySAC3` in the kernel driver
  (`bcm43xx.c:45`) and shows Android loads the patch and drives HCI over the raw UART.

### Nura consumer: BlueZ `hciattach bcm43xx`

BlueZ's `tools/hciattach_bcm43xx.c` resets the chip, reads the controller's local name,
then calls `bcm43xx_locate_patch(FIRMWARE_DIR, chip_name, …)`, which recursively scans for
a file whose name **starts with the local name** and ends in `.hcd`; it then downloads it
with `Write_RAM` (`bcm43xx_load_firmware`). `FIRMWARE_DIR` is `/etc/firmware` upstream
(`tools/hciattach.h`), but Alpine's bluez package applies
`004-Move-the-43xx-firmware-into-lib-firmware.patch`, changing it to **`/lib/firmware`**,
and ships `hciattach` in `bluez-deprecated` (Alpine `main/bluez/APKBUILD`). postmarketOS is
Alpine-based, so `/lib/firmware` is the effective search root.

Evidence for the basename: the ROM's own loader matches the chip string `BCM43438A1`
(case-insensitively; `toupper` is imported by `libbt-vendor.so`) and the blob itself
reports `BCM43438A1`. Installing the blob as **`BCM43438A1.hcd`** therefore satisfies the
case-sensitive `strncmp(chip_name, entry->d_name, strlen(chip_name))` check.

Mapping — `parity/firmware/files-bt.list`:

```
/vendor/firmware/bcm43438A1_V0051.0230.hcd -> /lib/firmware/postmarketos/samsung-j7elte/BCM43438A1.hcd
```

The directory prefix is not part of the ABI (`hciattach` scans recursively); it follows
the WiFi firmware convention already used by this project. A flat
`/lib/firmware/BCM43438A1.hcd` or `/lib/firmware/brcm/BCM43438A1.hcd` is equally
acceptable to this consumer, but is not listed to avoid duplicate blobs.

### Userspace bring-up that remains (G1)

Firmware installation is covered: the parent's `firmware-samsung-j7elte` pmaports package
(`parity/patches/pmaports/0003-firmware-samsung-j7elte-package.patch`, working tree
`parity/pmaports/device/archived/firmware-samsung-j7elte/`) installs both the bare
`BCM43438A1.hcd` and the ROM-named `bcm43438A1_V0051.0230.hcd` under
`/lib/firmware/postmarketos/samsung-j7elte/`. Nothing yet unblocks rfkill or attaches the
UART. Required:

1. Unblock the controller (the driver registers rfkill soft-blocked:
   `rfkill_init_sw_state(..., 0)` then `rfkill_set_sw_state(..., true)`,
   `bcm43xx.c:329-342`; unblocking calls `bcm43xx_bt_rfkill_set_power` and drives BT_EN):
   `rfkill unblock bluetooth`
2. Attach HCI and let `hciattach` download the patch (needs the P3 config fix):
   `hciattach -s 115200 /dev/ttySAC3 bcm43xx 3000000 flow`
   (device node from `BT_UPORT 3`; ROM used `/dev/ttySAC3` too).
3. Start `bluetoothd`; verify with `hciconfig -a` / `bluetoothctl show`.

Do **not** use bare `btattach` as the only step on this tree: with no `hci_bcm`/`btbcm` in
3.10, it attaches the line discipline but never downloads the patch-RAM firmware.

## Residual risks / tests

- **R1 (userspace gap):** the firmware is packaged (parent's `firmware-samsung-j7elte`,
  pmaports patch 0003), but nothing unblocks rfkill, runs `hciattach`, or starts
  `bluetoothd` yet. Until G1 is implemented, Bluetooth will not come up even after the
  config fix. Runtime check: `dmesg | grep '\[BT\]'`, `rfkill list`,
  `hciattach …`, `hciconfig -a`.
- **R2 (local-name uncertainty):** `hciattach` matches the controller's *Read Local Name*
  as a case-sensitive prefix. The blob and the ROM vendor library both name the chip
  `BCM43438A1`, so `BCM43438A1.hcd` is expected to match; if the controller reports a
  longer name (e.g. with a `UART` suffix), `hciattach` logs
  “Patch not found, continue anyway” and boots unpatched. Mitigation: read the name from
  the `hciattach` log/`hcitool` and add an exact-name symlink.
- **R3 (suspend behaviour — patched, needs runtime proof):** the DT patch restores the
  ROM's deep-sleep configuration for gpc4-2 (`con-pdn = 3`, BT_EN driven low in suspend)
  on all three revisions, and the patched DTBs compare identical to the ROM DTBs;
  runtime suspend/resume power behaviour still needs a measurement on hardware.
- **R4 (hciattach deprecation):** `hciattach` ships only in `bluez-deprecated`. A future
  BlueZ without it would need a mainline `btbcm.c`/`hci_bcm.c` backport (with firmware
  then at `brcm/BCM43430A1.hcd`, the mainline chip name for this die) plus a DT compatible
  the driver matches.
- **R5 (no runtime test):** no rootfs/boot test in this workspace and no kernel-code
  build was run (static symbol/DT/config comparison plus `cpp`+`dtc` DTB compile/compare
  and `git apply --check` only).
- **R6 (baud/flow):** the ROM vendor code runs HCI over `/dev/ttySAC3`; the exact line
  speed (3 Mbit/s in the example) and flow control were not observable from static data.
  Start with 115200/no custom speed and raise after `hciconfig -a` succeeds.
- **R7 (out-of-scope revisions):** `exynos7580-j7elte_usa_tmo_{00,01}.dts` still
  reference the shared gpa1-6 `bt_en` group (`:1530`, `:1486`). The stock ROM ships no
  USA-TMO DTB, so there is no ground truth for those boards; if they too carry BT_EN on
  gpc4-2, the same group fix would apply. Not part of `0001`.
