# BCM4752 (SM-J700M / j7elte) host wire protocol — recovered from stock `gpsd`

Slice: `GpsReProtocol`. Target: `/tmp/stock_gpsd` (stock `/system/bin/gpsd`, 4059464 B, ARM/Thumb-2,
bionic, stripped, ET_DYN). All addresses below are **file offsets == link-time VAs** (`.text` Addr `0x18990`
Off `0x18990`; `.rodata` Addr/Off `0x2f0570`), so they can be cited either way.

Method: linear Thumb-2 disassembly of `.text` (1 079 338 instructions; tools in
`/tmp/j7repo/code/gps/rework/` — `armdis.py`, `xref2.py`, `testconv.py`), ARM `.ARM.exidx`
symbolisation for function bounds, and a PIC-string/literal xref pass. The binary is a
position-independent image whose string refs are `ldr rX,[pc,#imm]` + `add rX,pc` (target = literal + pc;
verified statistically: 30 172 xref hits land exactly on known string starts vs 44 for the absolute reading),
and whose constant blobs are reached as `base + #offset` — the BRI frame templates are one such blob.

## 0. Bottom line

1. Wire = **BRI framing, `FE|FF 00 FD <cmd> [sub] [4B] FC`, 921600 8N1 CRTSCTS on `/dev/ttySAC0`**; no CRC,
   no seq, no escaping in BRI mode.
2. First thing on the wire after power-on is a **16×`0x80` autobaud burst**, then
   `FE 00 FD 00 00 55 AA 00 FF FC` ("get out of legacy"), then 6-byte `FF 00 FD 00 00 FC` (HW version) and
   `FF 00 FD 1F 95 FC` (debug SFR).
3. **No baud-change command** and **no NMEA-enable command** exist in the protocol; NMEA is generated by
   the host engine, and the chip speaks binary GLME (`0xE0`…`0x01`) after init.
4. The chip is **not hostless**: `gpsd` embeds the 8051 ESW/RAM patch in `.rodata` and uploads it over
   `0x61 17` frames before the GLME handoff, so no NMEA can appear until that download succeeds.

## 1. Transport

| Item | Value | Evidence |
|---|---|---|
| Device node | `/dev/ttySAC0` | `/etc/gps.xml` in stock `system.raw`: `PortName="/dev/ttySAC0"` |
| Line speed | **921600** 8N1 | same file: `BaudRate="921600"` |
| Flow control | hardware RTS/CTS (`crtscts`), plus 0x11/0x13 software flow control bytes (`PacketMgr::SetSwFlowControlXonXoff(0x%02X, 0x%02X)`) | `cfsetispeed`/`cfsetospeed`/`tcsetattr`/`ioctl` are the only termios imports (`readelf -sW`) |
| Power | sysfs `GpioNStdbyPath="/sys/class/sec/gps/GPS_PWR_EN/value"`, `GpioDelayMs="250"` | `/etc/gps.xml`; `BrcmGpsHalGpioSysfs.cpp` / `Power enable delay: %dms` @`0x2f0748` |
| RF config | `RfType="GL_RF_47520_BRCM_EXT_LNA"`, `FrqPlan="FRQ_PLAN_26MHZ_2PPM_26MHZ_300PPB"` | `/etc/gps.xml` |

There is **no baud negotiation over the wire**: the host fixes the UART at 921600 (from the XML), and the
chip's receiver adapts to that rate from the autobaud burst (§3 P1). No "set serial port / set baud"
message exists in the BRI command set (§5).

## 2. Framing

Host → chip (`Bri_SendAutobaud`, `Bri_GetOutOfLegacy`, `Bri_RequestHwVersion`, `Bri_RequestDebugSfr`):

```
<soff> <nwords> FD <cmd> [<sub>] [ <d0..d3> ] FC      6 or 10 B for control frames
soff   = FE  reliable/acknowledged frame
         FF  unreliable frame (queries)
nwords = 00  for every control frame in this binary (all 10 templates, §4)
         >00 word count of the payload for data-carrying frames (0x61 17 patch blocks)
```

Chip → host (only form the reply parser accepts):

```
FE 00 FD <cmd> <sub> <d0> <d1> <d2> <d3> FC      always 10 bytes
```

Properties, all verified in code:

* **No CRC/checksum and no sequence number on this link.** The `TXcrc/RXcrc/TXseq/RXseq` counters in the
  logs (`Serial_Errors: %sTXcrc %d` @`0x321d00`) belong to the separate glgps↔Android-HAL socket protocol,
  not to the UART.
* **Length comes from the header, not from a delimiter search**: `0xFC` terminates the frame, but payload
  bytes may themselves be `0xFC`, hence byte 1 must bound the frame — `00` for the fixed 6/10-byte control
  frames (and mandatory on replies: `ldrh buf[1..2]==0xFD00` @`0x2a7a64`), a payload word count for
  `0x61 17` patch writes [INFERENCE: byte-1 word count is taken from the open BCM4752 spec; this binary
  only ever shows `00` in its own control templates, and the block size is passed to
  `Bri_EswLoadBlockAndRequestCrc(0x%08lX, %luB)` @`0x34ce70`].
* **No escaping for BRI frames.** The low-level writer `0x2a599c` escapes byte `0xE0` only when the
  transport flag at `this+0x10E` is non-zero (`ldrb r3,[r6,#0x10e]; cmp r3,#0; beq 0x2a5a4e` @`0x2a59d6`,
  escape constant `mov.w sb,#0xe0` @`0x2a59f2`). In BRI/legacy transport mode that flag is 0 (also stated
  independently by the port's RE note in `patches/userspace/gps/0002-…`: "transport mode 1 … escaping
  disabled ([0x10e]=0)"). Escaping *is* used later for
  ESW/patch payloads — the log string `GlMeSrdAsicinit::Bri_EswLoadSetAsicData received unknown escaped
  character!` @`0x34cfe4` is the evidence.
* Reply validation `GlMeSrdAsicinit::Bri_CheckForReceivedPacket_Sardine` @`0x2a789c`:
  frame length must be exactly `0x0A` (`cmp r2,#0xa` @`0x2a78a8`), `buf[0]==0xFE` (`0x2a7a5a`),
  `ldrh buf[1..2] == 0xFD00` (i.e. `00 FD`, `0x2a7a64`), `buf[9]==0xFC` (`0x2a7a70`), then
  `cmd = buf[3]` (`+0x112`), `sub = buf[4]` (`+0x113`) and dispatch at `0x2a7a7a`:

| dispatch | condition | handler |
|---|---|---|
| patch/ESW CRC result | `cmd==0x2f && sub==0x15` | `0x2a7ad4` |
| HW/ASIC version | `cmd==0x00` | `0x2a7b60` |
| debug SFR / legacy status | `cmd==0x1f` | `0x2a7b96` |
| autobaud/bank sync | `cmd==0x21 && sub==0x00` | `0x2a7b2c` |
| anything else | — | "complete but garbage" counter (`0x34cf68`) |

## 3. Startup packet sequence

Order is fixed by the init state machine strings in `.rodata` `0x34c42c`–`0x34d1a8`
(`bri_wait4bri`, `bri_wait4asic_ready`, `INIT_STAGE A/B/C`, `INIT_STAGE: COMPLETE!`).

### P0 — power + standby (not protocol)
`write("1", /sys/class/sec/gps/GPS_PWR_EN/value)` then sleep 250 ms (`GpioDelayMs`). `nSTDBY`/reset GPIO
handling is `BrcmGpsHalGpio{Sysfs,Ioctl}.cpp` (`0x2f08a0`, `0x2f0a1c`). Our kernel-side PMIC/GPIO fix
(`sec_gps_bcm4752.c`: LDO10 `0x34/0xC0`, `GPS_PWR_EN=1`) already satisfies this.
**Reply:** none — chip is silent until P1.

### P1 — autobaud burst
```
80 80 80 80 80 80 80 80 80 80 80 80 80 80 80 80     (16 bytes, no framing/terminator)
```
Evidence: `GlMeSrdAsicinit::Bri_SendAutobaud()` @`0x2a5ae4`:
`movs r1,#0x80` @`0x2a5b02`, `movs r2,#0x10` @`0x2a5b04`, `blx memset@0x17af0` @`0x2a5b08`,
then 16-byte transport write `bl 0x2a599c` @`0x2a5b16`. Guarded by a static byte flag tested at
`0x2a5af8` (`ldrb r0,[r3]; cbnz 0x2a5b26`) → sent **once per daemon start**.
**Reply:** none to the burst itself; the chip's UART locks onto 921600 and answers P2.

### P2 — get out of legacy (the "wake"/handoff frame)
```
FE 00 FD 00 00 55 AA 00 FF FC   (10 B)
```
Evidence: `GlMeSrdAsicinit::Bri_GetOutOfLegacy` @`0x2a618c`; 10-byte copy from template
`0x398b2c` (`add.w ip,lr,#0x3d8` @`0x2a61d6` with base register `0x398754` resolved from literal
`0x000f257c`+pc), `movs r2,#0xa` @`0x2a61d2`, send `bl 0x2a5cd0` @`0x2a61ee`.
`0x55AA00FF` is the "leave legacy mode" token [INFERENCE: token semantics; the frame itself is exact].
Retried up to 4 trials
(`INIT_STAGE A: Resending Bri_GetOutOfLegacy %u!` @`0x34ca38`).
**Expected reply:** 10-byte `FE 00 FD 00 <sub> <4×ver> FC` (cmd `0x00`, handled @`0x2a7b60`), i.e. the
ASIC/IFC version; log `INIT_STAGE A: DONE. Version received: Asic 0x%08lX, IFC %lu, Radio 0x%02X`
@`0x34ca94`.

### P3 — request HW version
```
FF 00 FD 00 00 FC               (6 B)
```
Evidence: `GlMeSrdAsicinit::Bri_RequestHwVersion` @`0x2a6784`; template `0x398b38`
(`add.w r6,ip,#0x3e4` @`0x2a67be`, base `0x398754`), `movs r2,#6` @`0x2a67b8`.
**Expected reply:** `FE 00 FD 00 <sub> <v0 v1 v2 v3> FC`; the four payload bytes are assembled
little-endian into a `u32` at `this+0x140` @`0x2a7b60`–`0x2a7b88` and logged as
`GlMeSrdAsicinit::Got BRI HW version(0x%lx)` @`0x34cb48`. Byte 4 (`sub`) carries the radio/asic type byte.

### P4 — request debug SFR (legacy-mode probe)
```
FF 00 FD 1F 95 FC               (6 B)
```
Evidence: `GlMeSrdAsicinit::Bri_RequestDebugSfr` @`0x2a6104`; template `0x398b04`
(`add.w r6,ip,#0x3b0` @`0x2a613e`, base `0x398754`), `movs r2,#6` @`0x2a6138`.
**Expected reply:** `FE 00 FD 1F <sub> <d> ... FC`; `buf[5]` (`+0x114`) is copied to `this+0x13D`
@`0x2a7b96`–`0x2a7ba6` and drives `GlMeSrdAsicinit::Debugger detected/not detected` @`0x34c904/0x34c928`.
The sibling template `FF 00 FD 1F 94 FC` @`0x398afc` is the companion opcode (never referenced from the
bring-up path in this build).

### P5 — bank / partition handshake (start of the ESW loader)
```
FE 00 FD 61 16 00 00 00 00 FC   (10 B, bank byte at [5], "16" = change-bank op)
FE 00 FD 21 00 01 33 0E 10 FC   (10 B, sync after bank switch)
```
Evidence: both are built inline (not from the template blob):
* `fe 00 fd 61 16 …` at `0x2a5ce4`: `mov.w lr,#0x61` @`0x2a5d32`, `mov.w ip,#0xfd` @`0x2a5d2a`,
  `mov.w fp,#0x16` @`0x2a5d44`, `mov.w sl,#0xfe` @`0x2a5d14`, `movs r6,#0xfc` @`0x2a5d3e`.
* `fe 00 fd 21 00 <sub> 33 0e 10 fc` at `0x2a6d3e`–`0x2a6d80` (`movs r7,#0xfe` @`0x2a6d48`,
  `mov.w ip,#0xfd` @`0x2a6d4c`, `movs r4,#0x21` @`0x2a6d56`, `movs r7,#0x33` @`0x2a6d62`,
  `movs r6,#0x0e` @`0x2a6d60`, `mov.w ip,#0x10` @`0x2a6d6c`, `mov.w lr,#0xfc` @`0x2a6d52`).
  With `sub=1` this is exactly the 10-byte frame `FE 00 FD 21 00 01 33 0E 10 FC`.
Logs: `GlMeSrdAsicinit::Bri_EswLoadChangeBankAndRequestCheck(bank %u)` @`0x34c7c0`,
`bri_wait4eswbankswitch` @`0x34c800`, `Bank Switch Response: bank %u, %c` @`0x34c818`.
**Expected reply:** the sync frame echoed back as `FE 00 FD 21 00 … FC` (handler @`0x2a7b2c` stores
`buf[5..8]` to `this+0x13C` and signals stage 0x0b), plus bank-switch status.

### P6 — ESW/RAM patch download (the actual firmware upload)
```
FE <n> FD 61 17 DE C0 <addr_lo> <addr_hi> <data…> FC      (<=160 data B per write; <n> = word count)
FE 00 FD 21 18 <addr_lo> <addr_hi> <len_lo> <len_hi> FC   (verify / request CRC)
```
Evidence, local: `GlMeSrdAsicinit::Bri_EswLoadBlockAndRequestCrc(0x%08lX, %luB)` @`0x34ce70`,
`GlMeSrdAsicInitPatchLoader::GetBlock{Bank,Address,Data,Size,CheckSum,CRC}` @`0x34d424`–`0x34d534`,
`Patch CRC Received(0x%X, 0x%lX) %c` @`0x34cee0`, `bri_wait4eswbankloaded` @`0x34ceb0`,
`bri_wait4patchblockload` @`0x34cec8`, escaped-character path @`0x34cfe4`, and the
`0x61`/`0x21`/`0x2F 0x15` opcodes that are the only ones the reply parser dispatches on (§2).
Exact `61 17` / `21 18` byte layout matches an independent BCM4752 reimplementation
(<https://github.com/mbicz/bcm4752-init>, SPEC.md) — [INFERENCE] that this repo's layout applies verbatim;
the frame builder for it was not disassembled byte-for-byte here, only its `61 16` sibling (P5).
**Expected reply:** `FE 00 FD 2F 15 <4B value> FC` per block (the `0x2f/0x15` dispatch of §2, logged as
`Patch CRC Received(0x%X, 0x%lX)`), and further `FE 00 FD 21 18 … FC` acks.

### P7 — switch to high-speed clock / GLME handoff
```
FE 00 FD 00 00 55 AA 00 FF FC  …then   00 00 55 AA 00 FF
```
The `55 AA 00 FF` token is the "leave legacy / hand off" marker. After it the link no longer carries BRI
request frames: the chip runs the ESW just uploaded and both sides exchange **GLME** frames whose first
byte is `0xE0` — the low-level writer escapes exactly `0xE0` (@`0x2a59f2`/`0x2a5a00`), i.e. the daemon
sends `0xE0`-leading frames on the same UART after the handoff. Logs:
`INIT_STAGE B: Programming RF type and switch to high speed clock!` @`0x34d06c`,
`INIT_STAGE C: Starting Heartbeat, RTC capture, NvRam Read, ...` @`0x34d0e0`,
`INIT_STAGE: COMPLETE!` @`0x34d1a8`; then the measurement/RPC layer
(`GlMeSrdPacketManager`, `GlMeSrdTransactionManager`, "ESW_PRINTF:" @`0x32da44`) drives the session.
The chip's first post-handoff frame is reported as `e0 00 00 00 07 10 02 01 7e 06 30 02 00 05 50 e0 01`
by the independent BCM4752 reimplementation (<https://github.com/mbicz/bcm4752-init>) — [INFERENCE] for
our unit; no local capture exists yet.

## 4. Baud-change command

**None.** The complete set of BRI request templates in `.rodata` is 10 entries, all dumped from
`0x398afc`–`0x398b59` (`FE`/`FF` `00 FD … FC`, 6 or 10 B):

| addr | bytes | use |
|---|---|---|
| `0x398afc` | `FF 00 FD 1F 94 FC` | DebugSfr companion opcode, unused in this build |
| `0x398b04` | `FF 00 FD 1F 95 FC` | **P4** `Bri_RequestDebugSfr` |
| `0x398b0c` | `FE 00 FD 00 4D 80 00 00 00 FC` | write word `0x4D := 0x80` (unreferenced in bring-up path) |
| `0x398b18` | `FF 00 FD 00 4D FC` | read word `0x4D` |
| `0x398b20` | `FE 00 FD 00 4D 40 00 00 00 FC` | write word `0x4D := 0x40` |
| `0x398b2c` | `FE 00 FD 00 00 55 AA 00 FF FC` | **P2** `Bri_GetOutOfLegacy` |
| `0x398b38` | `FF 00 FD 00 00 FC` | **P3** `Bri_RequestHwVersion` |
| `0x398b40` | `FE 00 FD 00 1B 07 00 00 00 FC` | write word `0x1B := 7` |
| `0x398b4c` | `FF 00 FD 00 1B FC` | read word `0x1B` |
| `0x398b54` | `FF 00 FD 40 1A FC` | opcode `0x1A` with flag bit `0x40` |

Only `0x398b04`, `0x398b2c`, `0x398b38` are referenced from the bring-up code (bases `0x398754` +
`#0x3b0`/`#0x3d8`/`#0x3e4`); the other seven are either dead in this revision or reached through the
`FE 00 FD 61 17` path builders (P5/P6, inline immediates). None of them is a UART-configuration or
baud-rate command: every payload is a 32-bit register/word value or a mode/handshake token.

## 5. NMEA enable — there is none on the wire

The chip never emits NMEA in this product:

* Post-init the chip runs the binary **GLME** protocol (frames beginning `0xE0`; escape path
  `mov.w sb,#0xe0` @`0x2a59f2`, `cmp r2,#0xe0` @`0x2a5a00`), not NMEA.
* NMEA is produced **host-side** by the glgps engine and written to the Android HAL:
  `GL_NMEA[%s` @`0x2f56f8`, `GlEngineImplStd::GetNextNmeaSentence` @`0x311b14`,
  `GpsHalNmeaWrite: %s not ready for writing.` @`0x321c40`, `NmeaOutName`/`acNmeaOutName` @`0x2fc9cc`.
  Output sentences are standard NMEA plus proprietary `$PGLOR,…` (`0x33cfa4`–`0x33d6dc`) and `$PHAL,n`.
* The only NMEA-looking *input* to gpsd is the host control pipe (`$pglirm`, `IRM: Wrong NMEA address
  field … expected: $pglirm` @`0x32196c`) — that is HAL→daemon, not daemon→chip.

Consequence for our port: even a perfect P1–P4 handshake produces **zero NMEA**, because NMEA requires a
running chip (measurements + fix), which requires P6 (patch download) and the GLME handoff.

## 6. Is the chip "hostless"? No — the patch is embedded in `gpsd`

The stock daemon contains the 8051 ESW/RAM patch **inside its own `.rodata`** and uploads it over the BRI
link before the handoff (subject to the ROM fallback branch below):

* Loader call sites and state machine: `GlMeSrdAsicinit::Starting ESW loading: %s` @`0x34c988`,
  `esw_wait4version` @`0x34c9e8`, `GlMeSrdAsicInitEswLoader::GetDataToSend() %lu bytes [0x%lX->0x%lX[`
  @`0x34d2dc`, `GlMeSrdAsicInitPatchLoader::…` @`0x34d3c4`–`0x34d6dc`, patch-bank switch P5/P6.
* There is a ROM fallback branch `GlMeSrdAsicinit::No ESW Image to Load, using ROM` @`0x34c9b4` and
  `Patch will jump to ROM` @`0x34c56c` — these are *fallbacks*, not the normal path for
  `RfType=GL_RF_47520_BRCM_EXT_LNA`.
* The payload is present: `.rodata` above ~`0x390000` is dominated by binary images (8051 code plus data
  tables) — long-string density there drops to 3–23 per 32 KB block, and 8051 opcode-density profiling
  finds 16 KB windows at 0.79–0.85 (a random byte stream scores ~0.21).
  Sample at `0x3b0570`:
  `2D 40 03 | 75 45 01 | A2 04 | 92 05 | 85 45 49 | AD 3F AC 3E AF 3D | 12 F0 0B | 12 5C 8D |
   75 F0 45 | D1 49 | 44 04 | F0 7F 08 22 | 7F 10 22 | 75 A0 01 | 12 F4 F6`
  = `ADD A,R5 / JC / MOV 0x45,#1 / MOV C,0x04 / MOV 0x05,C / MOV 0x49,0x45 / MOV R5,0x3F …
  LCALL 0xF00B / LCALL 0x5C8D / MOV B,#0x45 / … MOV R7,#8 / RET` — i.e. 8051 code with
  `LCALL` targets inside the chip's 64 KB code space.
* No GPS firmware *file* exists anywhere in the stock image: `/system/bin` contains only `gpsd` and
  `gps.cer`, `/etc` only `gps.xml`/`gps.conf`; `/vendor/firmware` holds Bluetooth/camera/MFC blobs only
  (verified with `debugfs ls` on `system.raw`); `/etc/gps.xml` has no patch/ESW path key at all.

So the correct model is: **the host is required**; the ROM bootloader is alive and answers after the
autobaud burst, but it cannot produce measurements until `gpsd` pushes the embedded 8051 patch over
`0x61 17` frames.

## 7. What this means for the bring-up (j7elte)

* Our observed "chip silent at 4800…921600" is consistent with a chip that never received P1 at the
  right moment (power cycle → burst within the boot window) or whose UART clock/TCXO plan is wrong.
  The burst must be sent **after a real off→on of `GPS_PWR_EN`**, at 921600 8N1 with CRTSCTS.
* The in-repo daemon (`patches/userspace/gps/0002-…source.patch`, `src/j7elte-gpsd.c`) implements exactly
  P1–P4; each constant it uses was re-verified against the stock binary for this report:

  | daemon constant | bytes | stock evidence |
  |---|---|---|
  | `bri_autobaud` | `80`×16 | `0x2a5b02`/`0x2a5b04`/`0x2a5b16` |
  | `bri_get_out_of_legacy` | `FE 00 FD 00 00 55 AA 00 FF FC` | `0x2a618c`, template `0x398b2c`, len `#0xa` |
  | `bri_request_hw_version` | `FF 00 FD 00 00 FC` | `0x2a6784`, template `0x398b38`, len `#6` |
  | `bri_request_debug_sfr` | `FF 00 FD 1F 95 FC` | `0x2a6104`, template `0x398b04`, len `#6` |
  | RX framing `FE 00 FD … FC`, 10 B | — | parser `0x2a789c`, checks `0x2a7a5a`–`0x2a7a94` |

  It **cannot** produce NMEA by design: P5–P7 (bank switch, patch download, GLME)
  are absent, so a successful run proves only "chip alive + version".
* Acceptance signal for the daemon is therefore "10-byte `FE 00 FD 00 … FC` reply to P3", not NMEA.

## 8. Residual unknowns

1. Byte layout of the `61 17` patch-data and `21 18` verify frames: only the `61 16` sibling builder was
   disassembled (`0x2a5ce4`); the rest is inferred from the open reimplementation.
2. Purposes of the `0x4D`/`0x1B`/`0x1A`/`0x1F94` templates: they are register read/write pairs but no
   referrer exists in this build, so they are documented by shape only.
3. Which `RfType`-dependent ESW segment table is selected for `4752_B2` vs `4752_B3`
   (`0x34d218`/`0x34d220` name strings, xrefs at `0x2a87e4`, `0x2a8828`, `0x2a882e`): not resolved.
