# GPS parity — j7elte (Broadcom BCM4752)

**Verdict: PARITY (P1–P4 pass). No kernel patch required. No DT or config deltas found.**
GPS remains untested on Nura because no BCM4752-capable userspace daemon is packaged;
the kernel side (power-enable GPIO, `check_gps_op()` export, UART) is identical to the ROM.

Scope: `drivers/gps/sec_gps_bcm4752.c` (GPS power-enable + `check_gps_op()` export for the
Exynos power modes) and its DT node. Static verification only — no kernel build or
on-device test was performed (the 3.10 tree is not built by this task).

Reference points:
- ROM: `boot_out/symbols.txt`, `boot_out/vmlinux.elf`, `boot_out/dtbs/000_800.dts`
  (all three DTBs checked), `system.raw` (ext4; its root **is** `/system`, so `/etc/...`
  below means `/system/etc/...`), `boot_out/rd/init.samsungexynos7580.rc`.
- Nura tree `android_kernel_samsung_universal7580-2a746c1…` (baseline `b5e363a`), config
  `config-nura-j7elte`, sha512 `23e49e4993a98684717beaca7ea44f2cd4e0079460e573acc93237aa8b1d55115c72a22c0f16f3b8638c5b82ab57ea71ee8c043bf61d89f7cb190711e87d0156`,
  byte-identical to `parity/pmaports/device/archived/linux-samsung-j7elte/config-samsung-j7elte.aarch64`.
- DT: `arch/arm64/boot/dts/exynos7580-j7elte_rev00.dts`, `_rev04.dts`, `_rev06.dts`
  (the three variants built by `arch/arm64/boot/dts/Makefile:13` under `CONFIG_CAMERA_J7`),
  plus `exynos7580.dtsi`, `exynos7580-pinctrl.dtsi`, `exynos7580-j7elte_gpio_04.dtsi`.

The only other ROM names containing the driver tag are `__func__.34752` and
`__func__.44752` (`symbols.txt`, found by `grep 4752`). Those are compiler-generated
`__func__` string objects emitted for the `WARN()` sites; they carry no source identity
and are regenerated by any build. Excluding them, coverage is 5/5.

Behaviour equivalence was also checked in the ROM binary, because the driver is the only
consumer of the DT node and the ABI (`/sys/class/sec/gps/GPS_PWR_EN/value`) matters.
`samsung,exynos-bcm4752` occurs once in `vmlinux.elf` (file offset 0x9fa07c, VMA
`0xffffffc000bfdebc`); the function referencing it performs, in order:

1. `sec_device_create(NULL, "gps")` and a `BUG_ON` on failure;
2. `of_find_compatible_node(NULL, NULL, "samsung,exynos-bcm4752")`, `WARN` +
   `-ENODEV` on failure, using the string “failed to get device node of bcm4752”;
3. `of_get_gpio(node, 0)` and `gpio_is_valid` (bound 0x3ff), with the
   “Invalied gpio pin : %d” warning;
4. `gpio_request(gpio, "GPS_PWR_EN")`, warning “fail to request gpio(GPS_PWR_EN)”;
5. `gpio_direction_output(gpio, 0)`, `gpio_export(gpio, 1)`,
   `gpio_export_link(gps_dev, "GPS_PWR_EN", gpio)`; then returns 0, otherwise
   `sec_device_destroy()` and `-ENODEV`.

That is exactly `sec_gps_bcm4752.c:27-68` (including the `-ENODEV` value). The same
strings are present in the ROM `vmlinux.elf`, and `check_gps_op()` is called from
`arch/arm64/mach-exynos/exynos-powermode-smp.c:211,295` in the Nura tree, so the export
is required and present.

## P2 — Device tree: PASS, no deltas

### GPS node

ROM (`boot_out/dtbs/*.dts`, all three DTBs) and Nura (all three built j7elte variants)
are identical after phandle resolution:

| Property | ROM | Nura | Match |
|---|---|---|---|
| node | top-level `gps` | top-level `gps` | yes |
| `compatible` | `"samsung,exynos-bcm4752"` | `"samsung,exynos-bcm4752"` | yes |
| `gpios` | `<gpd2 6 0x1>` | `<&gpd2 6 0x1>` | yes |
| `status` | `"okay"` | `"okay"` | yes |
| regulators/clocks | none | none | yes |
| SPI | none | none | yes |

Evidence:
- ROM: `000_800.dts:5339-5343`, `001_19800.dts:5359-5363`, `002_32800.dts:5366-5370`.
- Nura: `exynos7580-j7elte_rev00.dts:1416-1420`, `_rev04.dts:1413-1417`,
  `_rev06.dts:1413-1417`.
- The ROM first cell is a phandle, not a number. It resolves to the `gpd2` bank in every
  DTB: `0x70` → `000_800.dts:1158-1164`; `0x71` → `001_19800.dts:1153-1159`;
  `0x7e` → `002_32800.dts:1154-1160`. Nura's label `&gpd2` is the same bank
  (`exynos7580-pinctrl.dtsi:581`). So all three ROM DTBs describe **gpd2 line 6,
  active-high, index 0** — the GPIO the driver reads with `of_get_gpio(root_node, 0)`.

### GPS power-enable pin (sleep state)

`gpd2-6` is the GPS enable. Both trees put it in the `pinctrl@139C0000` (Nura
`pinctrl_6`) sleep state:

- ROM `000_800.dts:1088` (`pinctrl@139C0000`), sleep-state at `:1595`,
  `gpd2-6` at `:1923-1927`: `pin-con-pdn=<0x00>`, `pin-pud-pdn=<0x01>`.
- Nura `exynos7580-j7elte_gpio_04.dtsi:107-110` (`&pinctrl_6`, `sleep6`) and `:209`:
  `PIN_SLP(gpd2-6, OUT0, DOWN)` → macros at `exynos_gpio_config_macros.dtsi:28-31,59-64`
  expand to `pin-con-pdn=<0>`, `pin-pud-pdn=<1>`. Exact match (output-low, pull-down).

### GPS UART (ttySAC0)

The daemon config opens `/dev/ttySAC0` (`gps.xml:5`), and the ROM init script chowns that
node (`init.samsungexynos7580.rc:332-333`). Both trees map `ttySAC0` identically:

- Alias: ROM `000_800.dts:2427` `uart0 = "/uart@13800000"`; Nura
  `exynos7580.dtsi:62` `uart0 = &serial_0`. The Samsung serial driver derives the
  `ttySAC<N>` index from the `uart` alias (`drivers/tty/serial/samsung.c:1916`).
- `serial_0`/`uart@13800000` properties are identical:
  `compatible="samsung,exynos5430-uart"`, `reg=<0 0x13800000 0x100>`,
  `interrupts=<0 421 0>` (ROM `0x1a5`), `pinctrl-0=uart0_bus` (gpb0-7..4, func 2),
  clocks `103/104/100` (ROM `0x67/0x68/0x64`), names
  `gate_pclk0/gate_uart0/sclk_uart0`
  (ROM `000_800.dts:2813-2822`; Nura `exynos7580.dtsi:506-515`).
- The four UART pin groups (`uart0-rts/cts/tx/rx`, gpb0-7..4) exist in both and have the
  same values: ROM `000_800.dts:5292-5331`; Nura `_rev04.dts:1380-1407`. The ROM node
  that references them, `serial@14C10000` (`000_800.dts:5335-5337`), exists verbatim in
  Nura (`_rev04.dts:1410-1412`); it has no `compatible` and is a dead/orphan node in
  **both** trees, so it has no runtime effect in either.
- UART sleep state for the GPS lines also matches: ROM `gpb0-4..7` at
  `000_800.dts:1623-1645` = input/up, out1/up, input/down, out0/down; Nura
  `exynos7580-j7elte_gpio_04.dtsi:151-154` (`GPS_RXD/TXD/CTS/RTS`).
- Console does not conflict: both `chosen` nodes use `console=ttySAC1,115200n8`
  (ROM `000_800.dts:4827`; Nura `_rev04.dts:26`), leaving UART0/ttySAC0 to GPS.

No regulator, clock, SPI or GPIO delta was found; the ROM `gps` node contains only the
three properties above.

- The NVRAM store is created at runtime in `/data/system/gps/` (`gps.xml:9`); it is not
  shipped in the ROM image and is not a firmware blob.

## Residual risks / untested behaviour

1. **No userspace consumer in Nura.** The pmaports device package
   (`device/archived/device-samsung-j7elte/APKBUILD`) depends only on
   `linux-samsung-j7elte`, `mkbootimg`, `postmarketos-base`; no gpsd/gnss daemon or
   BCM4752 driver is installed. The kernel will probe, create
   `/sys/class/sec/gps/GPS_PWR_EN/value`, expose `check_gps_op()` and leave ttySAC0 free,
   but there is no NMEA source until a daemon is packaged. This is why the Nura wiki lists
   GPS as untested.
2. **ROM binaries are not portable.** `gpsd`, `gps.default.so` and `libwrappergps.so` are
   Android/bionic closed-source userspace; they cannot run on postmarketOS without an
   Android compatibility layer. A Linux userspace needs a BCM4752-capable daemon (the
   chip is driven over ttySAC0, with GPS_EN power sequencing and NVRAM under
   `/data/system/gps/`).
3. **NVRAM is runtime state, not firmware.** On a converted device it will be regenerated
   on first fix; `/data/system/gps` must be writable by the daemon user.
4. **No build/boot test.** No kernel build was attempted; verification is
   source/symbol/DT/config/binary comparison. `git apply --check` is not applicable
   because no patch is produced.
5. The `serial@14C10000` node and the `pinctrl@14CC0000` pin groups are inherited cruft in
   both trees; the node is not bound by any driver, so it neither helps nor breaks GPS.
