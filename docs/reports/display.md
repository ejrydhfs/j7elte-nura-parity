# Display parity — Exynos7580 DECON fbdev + MIPI DSIM + ea8061 (j7elte)

**Verdict: PARITY (P1–P4 pass). No kernel patch. No firmware.**
The Nura display stack is at parity with the ROM for j7elte rev00 and also for rev04/rev06:
besides GCC clones and the ROM's older two-level panel-ops plumbing (both explained below),
every ROM display symbol is implemented. The only config delta (MDNIE_LITE) compiles dead code
for this panel. The "display manager does not show" symptom is userspace/architecture:
the kernel (ROM and Nura alike) exposes only fbdev, no DRM.

Ground truth: ROM `3.10.61` (`boot_out/symbols.txt`, `boot_out/dtbs/*.dts`), Nura tree
`android_kernel_samsung_universal7580-2a746c1` @ baseline `b5e363a`, `config-nura-j7elte`,
`parity/pmaports` @ `ba682bd`. Static verification only — no kernel build was performed (a
cross toolchain exists at `…/j7rom/../toolchains/gcc-arm-10.3-2021.07-x86_64-aarch64-none-linux-gnu/`
and system `aarch64-linux-gnu-objdump`; only `objdump` was used here); runtime behavior is
untested.

## Method note (ROM disassembly)

`boot_out/vmlinux.elf` places code **0x11c0 bytes earlier than the kallsyms addresses**: the ELF
LOAD maps `kernel.bin` offset 0x1c0 to `0xffffffc000204000`, while `kernel.bin` offset 0 is
`_text = 0xffffffc000205000` (nm). Consequently `objdump -d vmlinux.elf` labels are correct but
the decoded bytes are mid-function. All disassembly below uses the corrected mapping:

```
aarch64-linux-gnu-objdump -D -b binary -m aarch64 --adjust-vma=0xffffffc000205000 \
    --start-address=<addr> --stop-address=<addr2> boot_out/kernel.bin     # file offset = addr - 0x205000
```

Data structures were read directly from `kernel.bin` with the same mapping. **This also affects
every other driver's disassembly analysis** (verified: 0/84 prologue matches at raw ELF labels,
correct prologues after the 0x11c0 correction).

1. **GCC inter-procedural clones** (present, no separate source symbol):

   `decon_map_ion_handle.isra.18` → `decon_map_ion_handle`;
   `dsim_dump.isra.12` → `dsim_dump`;
   `dsim_reg_enable_pll.part.0` → `dsim_reg_enable_pll`;
   `dsim_wait_for_cmd_fifo_empty.isra.8` → `dsim_wait_for_cmd_fifo_empty`;
   `mdnie_no.22025` → `static unsigned int mdnie_no` (`mdnie_lite.c:688`).

2. **`decon_bw` (the one symbol the earlier pass flagged)** — not a function and not missing.
   Nura: `static unsigned int decon_bw, cam_bw, total_bw;` in `drivers/bts/bts-exynos7580.c:185`
   (used at :1609-1629). It appears in ROM kallsyms because the ROM is built with
   `CONFIG_KALLSYMS_ALL`; Nura also has `CONFIG_KALLSYMS_ALL=y` (config:153), so a build of the
   same source exposes it identically. **Do not patch.**

3. **ROM's older two-level panel framework** (`mipi_dsim_lcd_driver` → `dsim_panel_ops`):
   * `ea8061_panel_ops` — data symbol at ROM `0xffffffc000f03ff8`, contents
     `{ea8061_early_probe, ea8061_probe, ea8061_displayon, ea8061_exit, ea8061_init, 0, 0, 0xf}`.
   * `ea8061_early_probe` — ROM `0xffffffc00049ecb0`: `mov w0, #0; ret` (**no-op**).
   * `dsim_panel_resume` — ROM `0xffffffc00049ecb8`: `mov w0, #0; ret` (**no-op**).
   * `dsim_panel_early_probe` — ROM `0xffffffc00049fff0`: stores `dsim_panel_get_priv_ops(dsim)`
     at `dsim+0x3a0` and tail-calls `ops->early_probe` if non-NULL.
   * `dsim_panel_get_priv_ops` — returns the board-ops pointer.
   In Nura the callbacks live directly in `struct mipi_dsim_lcd_driver`
   (`dsim.h:141-149`: early_probe/probe/suspend/displayon/resume/display_lvds_init) and
   `dsim_drv.c` calls them through `call_panel_ops()`, which is NULL-safe
   (`dsim.h:52-53: (((q)->panel_ops->op) ? ((q)->panel_ops->op(args)) : 0)`), so the two
   ROM no-ops have no replacement and are not needed. Nura's `ea8061_mipi_lcd_driver`
   (`ea8061_lcd_ctrl.c:1635`) provides `.probe/.displayon/.suspend`.

4. **Panel-path behavioural equivalence** (ROM binary vs Nura source):
   * ROM `ea8061_displayon` (`0x49ecc0`, 0x28 B) is a `dev_info(... "MDD : %s was called")` stub
     returning 0 — identical to Nura `ea8061_lcd_ctrl.c:842-854`.
   * ROM `ea8061_exit` (`0x49ece8`) writes DISPLAY_OFF, `msleep(35)` (`mov w0,#0x23`), SLEEP_IN,
     `msleep(150)` (`mov w0,#0x96`) — identical to Nura `ea8061_lcd_ctrl.c:856-879`.
   * ROM command arrays at `0x9b4478`/`0x9b4480` are `28 00 00` / `10 00 00`, byte-identical to
     Nura `SEQ_DISPLAY_OFF` / `SEQ_SLEEP_IN` (`ea8061_param.h:114-122`).
   * ROM `.rodata` contains the source names `ea8061_displayon`, `ea8061_exit`, `ea8061_probe`,
     `ea8061_read_init_info` (0x9b4450-0x9b4488), matching Nura function names.
   * ROM `ea8061_probe` calls `dsim_write_hl_data`/`dsim_read_hl_data` + `generate_volt_table`/
     `cal_gamma_from_index`; Nura `ea8061_probe` (`:1123`) → `ea8061_read_init_info` (`:769`) →
     `init_dimming` (`:666`) calls the same helpers (`dimming_core.c:428,645`).

## Cause of "Screen = Partial / display manager does not show"

Conclusion: **userspace/architecture, not a kernel parity gap. Do not fabricate a kernel patch.**

Evidence:
1. Kernel display works: `/dev/fb0` is registered unconditionally at probe
   (`decon_core.c:4591`), panel is video-mode (continuous scanout), and the boot splash renders
   through fb0 — consistent with the wiki's "splash renders".
2. There is no DRM device to hand to a compositor: `CONFIG_DRM` is not set (config:2262), the
   tree has no DRM/KMS driver for DECON, so `/dev/dri/card0` cannot exist.
3. The ROM is in the same situation — no DRM subsystem symbols in ROM kallsyms — and Android
   drives the same vendor fbdev. So this is not a ROM→Nura regression.
4. Wayland/KMS display managers (phosh, Plasma Mobile, etc.) require a DRM device; they cannot
   start on a pure fbdev kernel. The fix is a userspace choice (fbdev-capable UI/backend or an
   out-of-tree DRM shim), not a driver change.
5. No silent deferred-probe trap: `drivers/video/exynos/decon_7580/` contains no
   `EPROBE_DEFER` handling at all (grep = 0 hits), so the decon/dsim/panel probes either
   complete (`/dev/fb0`, `/sys/class/backlight/panel`) or fail loudly in `dmesg` — a
   half-initialized display cannot sit on the deferred list after boot.

Related note: pmaports applies `fix-argb.patch` on top of the kernel tree, flipping R/B offsets
in `decon_check_var()` for 24 bpp requests (`decon-int_drv.c:388`, patched hunk at :453). It is a deliberate
userspace pixel-format workaround, not a ROM gap; if an fbdev UI renders BGR vs RGB incorrectly,
inspect that patch first.

## Residual risks / test plan

* Static verification only: symbol/DT/config/source and ROM-binary checks; no kernel build and
  no runtime test was performed here.
* Hardware runtime checks for whoever boots it: `ls -l /dev/fb0 /dev/dri`,
  `cat /sys/class/graphics/fb0/virtual_size`, `cat /sys/class/lcd/panel/lcd_type`,
  `cat /sys/class/backlight/panel/brightness`, `dmesg | grep -E 'decon|dsim|ea8061'`,
  write a pattern to fb0 and confirm it appears (video mode ⇒ immediate).
* Board revisions >3: Nura rev04/rev06 DTBs verified equal to ROM by static DT comparison only;
  the extra gpd1 low pulse in the rev4/6 power-off sequence is not exercised in this analysis.
* MDNIE absent vs ROM: only Android HAL consumers would notice; no fbdev/DM impact.
* `CONFIG_DECON_LPD_DISPLAY`/`CONFIG_DECON_BLOCKING_MODE` are off in Nura; ROM cannot be proven
  either way from symbols (their handler functions are unconditional in this source), so no
  claim of a delta is made.
